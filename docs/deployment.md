# Deployment

Configure the variables in `.env.example`. Compose runs PostgreSQL, authenticated Redis, API, independent worker and frontend/Nginx. Judge0 remains an explicit externally provisioned dependency. The existing Compose project name `coder` is retained for its volume association; no existing volumes are deleted.

Fresh database: `docker compose up --build -d` applies committed migrations through the API startup script. The worker starts after API liveness succeeds. Seed with `docker compose exec api node dist-seed/seed.js`. No accounts or fake statistics are seeded. Bootstrap with explicitly configured ADMIN_EMAIL/ADMIN_USERNAME/ADMIN_PASSWORD using `node dist/bootstrapAdmin.js`, then remove that password from deployment configuration.

Existing databases initialized with db push: take a tested backup, compare the database to the committed baseline migration, then mark only that baseline as applied with `npx prisma migrate resolve --applied 202610150001_baseline`. Run `npx prisma migrate deploy` to apply the judging migration. Do not baseline a fresh/unknown schema or reset a populated database. Existing terminal rows are backfilled; historical Run rows cannot be identified automatically. Review legacy seed accounts and rotate/remove known demo credentials manually after identifying them; new code never seeds those accounts.

Production requires TLS, COOKIE_SECURE=true, strong independent secrets, database backups, private execution ingress and egress controls. API and worker containers use the Node non-root user. PostgreSQL/Redis/provider ports are not published by the app stack. Optional MinIO is not deployed; configure it separately for avatars. Payments and OAuth are not prerequisites for judging.

Operations: `docker compose logs -f api worker`, `docker compose restart api worker`, `docker compose down`. Run `docker compose exec api npm run retention` on an operator schedule. WORKER_CONCURRENCY bounds local processing; GLOBAL_EXECUTION_CONCURRENCY separately bounds provider requests across replicas through Redis leases. A crashed worker can hold a lease until its twenty-minute expiry. User admission is coordinated by PostgreSQL user-row locks. Worker heartbeat and queue counts are available to admins; `/ready` checks database, Redis, worker heartbeat and provider reachability. Liveness alone does not prove execution works.

Validation in this environment: Docker images were built and the actual Compose app started. The existing database volume is PostgreSQL 15; Compose now defaults to that version instead of attempting to open it with PostgreSQL 17. The old app schema was compared to the baseline, backed up, baselined and migrated without resetting data. Redis health checks use the configured password through REDISCLI_AUTH. The app loads missing original content on startup, controlled by SEED_CONTENT_ON_START (true by default).

Live checks confirmed 29 published questions and one 22-module course, browser pagination, password login, problem/course draft authoring, Google/GitHub authorization redirects and a basic real Python execution returning Accepted. Existing accounts and the original two questions were preserved. Personal provider consent, SMTP/payment delivery and hostile-code sandbox restrictions remain outside these checks. A successful basic execution does not prove sandbox escape resistance.

Windows shortcuts: `Start-CodeForge.ps1` starts/rebuilds and checks the local site; `Create-Admin.ps1` securely prompts for a new administrator without shipping default credentials. Existing deployments can set POSTGRES_VERSION to their current major version; upgrading a database requires a proper backup/restore or pg_upgrade workflow, not just an image tag change.
